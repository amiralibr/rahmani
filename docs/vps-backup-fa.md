# پشتیبان PostgreSQL و تمرین بازیابی روی VPS

**دامنه:** پایگاه `rahmani` در Compose فعلی (PostgreSQL 17). این پشتیبان شامل اطلاعات محرمانه است. فایل‌های خارج از پایگاه، کد، تنظیمات محیط، کلید MFA، تنظیمات دامنه و TLS را پوشش نمی‌دهد. رازهای لازم برای راه‌اندازی مجدد را جداگانه در مخزن امن مرکز نگهداری و بازیابی‌شان را آزمایش کنید. این روش بازیابی به یک نقطهٔ زمانی بین دو پشتیبان را فراهم نمی‌کند.

۱. روی میزبان امنِ بازیابی، با OpenSSL 3 جفت کلید بسازید. کلید خصوصی باید رمزدار و مستقل از VPS باشد. گذرواژه را در خط فرمان وارد نکنید.

```sh
umask 077
openssl req -x509 -newkey rsa:3072 -sha256 -days 365 -subj '/CN=Rahmani Backup Recipient' -keyout restore-key.pem -out backup-cert.pem
openssl x509 -in backup-cert.pem -noout -fingerprint -sha256
```

۲. **فقط گواهی عمومی** را به VPS انتقال دهید، اثرانگشت را از مسیر مستقل کنترل کنید و فایل را در مسیری قرار دهید که کاربر غیرمجاز نتواند جایگزین کند. از ریشهٔ پروژه اجرا کنید:

```sh
BACKUP_DIR=/var/backups/rahmani BACKUP_CERT=/etc/rahmani/backup-cert.pem ./ops/backup
```

اسکریپت خروجی `pg_dump` را بدون فایل میانیِ متن‌باز با AES-256-GCM در قالب CMS رمز می‌کند. نام فایل کامل را فقط در صورت موفقیت چاپ می‌کند. فایل رمز‌شده را در ذخیره‌ساز جدا از VPS با دسترسی محدود نگه دارید. مرکز باید فاصلهٔ پشتیبان‌ها، مدت نگهداری و زمان قابل‌قبول بازیابی را تعیین کند؛ اجرای زمان‌بندی‌شده، انتقال خارج از میزبان و هشدار شکست به‌صورت خودکار نصب نشده‌اند. پیش از چرخش کلید، پشتیبان جدید را آزمایش و کلیدهای قدیمیِ لازم را تا پایان دورهٔ نگهداری حفظ کنید.

۳. روی **میزبان بازیابی مورد اعتماد** با Docker، تصویر `postgres:17-alpine` و OpenSSL 3، نسخهٔ منتقل‌شده را امتحان کنید:

```sh
BACKUP_KEY=/secure/restore-key.pem BACKUP_CERT=/secure/backup-cert.pem ./ops/restore-drill /secure/archives/NAME.dump.cms
```

تمرین، یک PostgreSQL موقت بدون شبکهٔ خارجی یا پورت منتشرشده می‌سازد، آرشیو را بازیابی می‌کند و خواندن جدول‌های اصلی را بدون چاپ اطلاعات مراجع می‌آزماید. پایگاه عملیاتی مقصد این فرمان نیست. در پایان عادی یا خطا، کانتینر و حجم موقت حذف می‌شوند؛ بعد از قطع برق یا توقف اجباری، باقیمانده‌ها را روی میزبان تمرین بررسی کنید. میزبان باید برای دادهٔ رمزگشایی‌شده فضای کافی و دیسک محافظت‌شده داشته باشد. فقط آرشیو با منشأ مورد اعتماد را بازیابی کنید؛ رمزنگاری با کلید عمومی جایگزین کنترل منشأ آرشیو نیست.

۴. تاریخ پشتیبان، نتیجه و مدت تمرین و نسخهٔ نرم‌افزار را بدون اطلاعات شخصی ثبت کنید. **موفقیت این تمرین جای آزمون برنامه نیست:** پیش از انتقال ترافیک، روی محیط جداگانه با ارسال پیام و درگاه پرداخت غیرفعال، ورود MFA، دسترسی‌ها و خلاصه‌های مالی را کنترل کنید. راه‌اندازی جایگزین، چرخش اعتبارنامه و ابطال نشست‌ها نیاز به تصمیم مسئول عملیات دارد؛ هیچ جابه‌جایی خودکار به پایگاه بازیابی‌شده انجام نمی‌شود.

### تمرین خودکار بازیابی با PostgreSQL واقعی، بدون Docker

با کاربر غیر root روی میزبان آزمایشی لینوکس، ابزارهای `initdb`، `pg_ctl`، `pg_dump` و `pg_restore` از یک نسخهٔ PostgreSQL را در `PATH` قرار دهید. پس از نصب وابستگی‌های API و `npm run build` در `apps/api`، از ریشهٔ پروژه `ops/tests/postgres-restore.sh` را اجرا کنید. این فرمان خودش دو کلاستر خالی روی سوکت‌های خصوصی می‌سازد؛ به پایگاه عملیاتی وصل نمی‌شود. مبدأ پیش از راه‌اندازی مقصد متوقف می‌شود. آرشیو و کلید آزمایشی با پایان تمرین حذف می‌شوند.

در اجرای محلی با PostgreSQL 16.2 و دادهٔ ساختگی، پس از بازیابی آرشیو رمز‌شده ورود به API با حساب MFA بازیابی‌شده موفق بود. گزارش استرداد برای کاربر بدون ورود ۴۰۱ داد و برای حساب مجاز همان پرونده و جمع مصوب ۴۰۰٬۰۰۰ ریال بدون رسید را نشان داد. آخرین اجرای محلی حدود ۲ ثانیه از آغاز `pg_restore` تا پایان بررسی برنامه طول کشید؛ این عدد شامل آماده‌سازی کلاسترها نیست و تخمین زمان بازیابی VPS محسوب نمی‌شود. برای پذیرش عملیاتی، مسیر Docker با PostgreSQL 17، نسخهٔ خارج از میزبان و اندازهٔ واقعی پایگاه باید جداگانه آزمایش شود.

### زمان‌بندی، انتقال مستقل و هشدار شکست

نمونه‌های `ops/systemd/` برای VPS لینوکسی با systemd هستند و **خودکار نصب نشده‌اند**. فرض مسیر نصب `/opt/rahmani` است. اگر مسیر دیگری دارید، `WorkingDirectory` و `ExecStart` را در واحدها اصلاح کنید. واحدها با حساب root اجرا می‌شوند؛ کد پروژه، فایل‌های محیط و تنظیمات SSH باید فقط برای مدیر قابل‌نوشتن باشند.

۱. روی **میزبان دیگری** فضای SFTP با حساب اختصاصی ایجاد کنید. دایرکتوری ورود آن حساب مقصد انتقال است و باید `put`، `get` و `rename` را پشتیبانی کند. اثرانگشت کلید میزبان را از مسیر مستقل تأیید و در `/etc/rahmani/backup_known_hosts` ثبت کنید. در `/etc/rahmani/backup_ssh_config` یک `Host rahmani-offsite` با `HostName`، `User`، `IdentityFile` و `IdentitiesOnly yes` تنظیم کنید. کلید انتقال با کلید خصوصی رمزگشایی متفاوت است؛ کلید رمزگشایی روی VPS لازم نیست. برای مقاومت در برابر حذف یا باج‌افزار، نسخه‌بندی یا نگهداری تغییرناپذیر را جداگانه در مقصد فعال کنید.

۲. فایل `/etc/rahmani/backup.env` را با مجوز ۶۰۰ بسازید:

```ini
BACKUP_DIR=/var/backups/rahmani
BACKUP_CERT=/etc/rahmani/backup-cert.pem
BACKUP_SSH_CONFIG=/etc/rahmani/backup_ssh_config
BACKUP_KNOWN_HOSTS=/etc/rahmani/backup_known_hosts
```

۳. نصب و آزمایش اولیه، از ریشهٔ پروژه و با اختیار مدیر:

```sh
install -m 644 ops/systemd/rahmani-backup* /etc/systemd/system/
systemctl daemon-reload
systemctl start rahmani-backup.service
journalctl -u rahmani-backup.service -n 30
```

فقط پس از موفقیت انتقال، آرشیو را از مقصد روی میزبان امن بازیابی و تمرین مرحلهٔ ۳ را اجرا کنید. سرویس پیش از نهایی کردن نام فایل مقصد، کل فایل رمز‌شده را بازمی‌خواند و بایت‌های آن را مقایسه می‌کند؛ برای این کار فضای یک کپی موقت و پهنای باند رفت‌وبرگشت لازم است. در شکست انتقال یا اختلاف بایت، فایل محلی باقی می‌ماند؛ فایل `.part` مقصد را آرشیو کامل تلقی نکنید. نگهداری و پاک‌سازی فایل‌ها باید طبق سیاست مرکز باشد.

۴. برای هشدار، MTA سازگار با `/usr/sbin/sendmail` و هدایت ایمیل `root` به مسئول عملیات لازم است. پیش از فعال‌سازی، با `systemctl start rahmani-backup-alert.service` دریافت ایمیل آزمایشی را کنترل کنید. سپس `systemctl enable --now rahmani-backup.timer` و `systemctl list-timers rahmani-backup.timer` را اجرا کنید. زمان پایه ۰۲:۰۰ UTC با حداکثر ده دقیقه تأخیر تصادفی است و اجرای ازدست‌رفته پس از روشن‌شدن جبران می‌شود. شکست سرویس، واحد هشدار را فراخوانی می‌کند؛ تحویل ایمیل مستقل از خروجی موفق sendmail است. برای تشخیص خاموشی میزبان یا اجرا نشدن تایمر، آخرین نسخهٔ موفق را از بیرون VPS نیز پایش کنید. توقف زمان‌بندی: `systemctl disable --now rahmani-backup.timer`.

### تمرین از روی نسخهٔ خارج از میزبان

پس از موفقیت `backup-offsite`، آخرین سطر خروجی شامل SHA-256 فایل رمز‌شده و نام نهایی آن است. **این دو مقدار را از مسیر مورد اعتماد جدا از مخزن SFTP** (مثلاً ثبت وقایع محافظت‌شدهٔ عملیات) برای تیم بازیابی نگه دارید. هشِ خوانده‌شده از کنار همان آرشیو در مخزن، جایگزین این کنترل نیست. هش امضای دیجیتال یا اثبات سلامت پایگاه مبدأ نیست.

روی میزبان بازیابی با حساب SFTP ترجیحاً فقط‌خواندنی، کلید میزبان از پیش تأییدشده و تصویر `postgres:17-alpine`، متغیرهای `BACKUP_SSH_CONFIG`، `BACKUP_KNOWN_HOSTS`، `BACKUP_CERT` و `BACKUP_KEY` را طبق بخش‌های قبل تنظیم کنید. سپس از ریشهٔ پروژه اجرا کنید:

```sh
./ops/restore-offsite "$ARCHIVE_NAME" "$TRUSTED_SHA256"
```

این فرمان فایل نهایی را از مخزن می‌خواند، نه از نسخهٔ محلی VPS. نام موقت یا مسیر دلخواه پذیرفته نمی‌شود. اگر هش یکسان نباشد، رمزگشایی و شروع کانتینر انجام نمی‌شود. در صورت تطابق، تمرین جداگانهٔ PostgreSQL اجرا و در پایان فایل موقت پاک می‌شود. خروجی زمان بازیابی و بررسی جدول‌ها را می‌دهد (نه زمان انتقال). برای سنجش کل زمان از `time` پیش از فرمان استفاده کنید. بازیابی مستقیم روی سرویس عملیاتی انجام نمی‌شود. برای نسخه‌های قدیمی بدون هش مستقل، برابری با نسخهٔ اولیه را تأییدشده تلقی نکنید.
