# مرکز دکتر رحمانی — نمونهٔ طراحی
صفحهٔ فارسی و واکنش‌گرا؛ انتخاب خدمت فقط یک پیش‌نمایش است. فقط فرم تماس، ایمیل و موضوع را با رضایت کاربر ذخیره می‌کند. تصویر صفحه نمایشی است، نه معرفی یک متخصص واقعی.

## پیش‌نمایش محلی
`cd apps/web && npm ci && npm run dev`

رابط اصلی اکنون Next.js، React و TypeScript است. صفحات `/` و `/profile/` فارسی و مسیرهای `/en/` و `/en/profile/` انگلیسی هستند. برای ساخت تولیدی `npm run build` اجرا شود.

## استقرار نسخهٔ نمایشی روی VPS
روی میزبان دارای Docker و Compose پس از تنظیم رمز طبق بخش درخواست تماس، از ریشهٔ مخزن `docker compose up -d --build` اجرا کنید. سایت از `http://127.0.0.1:8080` روی خود VPS قابل بررسی است. برای انتشار، دامنه را به VPS وصل کنید و reverse proxy دارای HTTPS را روی میزبان به همین آدرس متصل کنید. خروجی Next.js و سرور NestJS در تصویر نهایی قرار دارند؛ اسناد پروژه منتشر نمی‌شوند. برای توقف `docker compose down` اجرا کنید.

## مبنای طراحی و ادامهٔ کار
مرجع UI UX Pro Max: ردیف Medical Clinic در colors.csv (سبز تیره و زمینهٔ روشن)، رنگ مکمل بنفش از Mental Health App و قواعد Focus States و Keyboard Navigation در ux-guidelines.csv. فونت وزیرمتن و آیکون‌ها محلی هستند. در هر مرحله الگوی انتخاب‌شده و نتیجهٔ بررسی موبایل، صفحه‌کلید و کنتراست ثبت شود.

پیش از ساخت رزرو واقعی: مؤسسه باید مدت نگهداری موقت نوبت، زمان قطعی‌شدن رزرو، مهلت لغو و بازپرداخت و نقش‌های مجاز را تأیید کند. معیار پذیرش بعدی: دو درخواست هم‌زمان نباید برای یک زمان دو نوبت قطعی بسازند و بازگشت از درگاه بدون تأیید سرور پرداخت موفق محسوب نشود. احراز هویت هنوز پیاده‌سازی نشده است.

## مرز نمونهٔ فعلی با محصول نهایی
فایل‌های ایستای `site/` صرفاً نمونهٔ بصری هستند، نه پایهٔ کدنویسی محصول. مرجع معماری، بخش‌های ۴، ۵ و ۱۱ سند «سایت روانشناسی دکتر رحمانی.docx» است: معماری یکپارچهٔ ماژولار، رابط Next.js / React / TypeScript، بک‌اند NestJS و پایگاه دادهٔ PostgreSQL. چیدمان پیشنهادی شامل apps/web، apps/admin، apps/api، apps/worker و بسته‌های مشترک ui، types، config و i18n است. برای درخواست تماس از TypeORM استفاده شده است. Docker فعلی فقط برای پیش‌نمایش است. تصویر مشاور مرد نمایشی است و پرترهٔ دکتر رحمانی نیست.

## آکادمی — کاتالوگ نمایشی
مسیرهای `/academy/` و `/en/academy/` فیلتر شیوهٔ برگزاری و صفحات اختصاصی سه دورهٔ نمونه دارند. جلدها از سبک Claymorphism در UI UX Pro Max الهام گرفته‌اند و بدون کتابخانهٔ سه‌بعدی ساخته شده‌اند. هیچ شهریه، مدرس، گواهی یا ظرفیت واقعی اعلام نشده و ثبت‌نام فعال نیست.

## مجلهٔ آموزشی
مسیرهای `/journal/` و `/en/journal/` شامل جست‌وجو، فیلتر موضوعی و سه یادداشت آموزشی عمومی هستند. محتوا در `apps/web/app/articles.ts` نگهداری می‌شود؛ پنل انتشار و تأیید علمی هنوز پیاده‌سازی نشده است.

## درخواست تماس (WEB-07) و اجرای کامل
صفحات `/contact/` و `/en/contact/` به `POST /api/v1/contact-requests` روی همان دامنه متصل‌اند. NestJS، TypeORM و PostgreSQL فقط ایمیل، موضوع، زبان، زمان و نسخهٔ رضایت را نگهداری می‌کنند. جدول `contact_requests` با migration ساخته می‌شود؛ مسیر عمومی برای خواندن درخواست‌ها وجود ندارد. پاسخ موفق ۲۰۱ دارای `reference` است. فهرست پذیرش، ورود کارکنان و ارسال ایمیل هنوز فعال نیستند. پیش‌نمایش را فقط با ایمیل آزمایشی امتحان کنید.

روی VPS ابتدا در پوشهٔ پروژه `umask 077; printf 'POSTGRES_PASSWORD=%s\n' "$(openssl rand -hex 32)" > .env` را **فقط برای راه‌اندازی نخست** اجرا کنید؛ سپس `docker compose up -d --build`. پایگاه داده پورت عمومی ندارد. رمز و volume را حفظ کنید (از `down -v` استفاده نکنید). این نسخه برخلاف نمونهٔ ایستا به PostgreSQL نیاز دارد. NestJS صفحات خروجی و API را با هم ارائه می‌کند. پیش از استفادهٔ عملی، HTTPS، دسترسی کارکنان، سیاست حذف اطلاعات و پشتیبان‌گیری/تست بازیابی باید آماده شوند. محدودیت فعلی ۱۵ درخواست در ۱۵ دقیقه برای هر IP قابل مشاهده توسط سرور است؛ پشت پراکسی مشترک ممکن است سقف بین کاربران مشترک باشد.

## حساب کارکنان و میز پذیرش
بعد از راه‌اندازی سرویس‌ها، روی VPS برای یک اپراتور `docker compose exec web node dist/staff-cli.js create sara reception` اجرا کنید. برای دسترسی فقط خواندنی به جای `reception` از `viewer` استفاده کنید. رمز تصادفی فقط در همان ترمینال نمایش داده می‌شود؛ آن را در مدیر رمز نگه دارید و در چت نفرستید. `docker compose exec web node dist/staff-cli.js disable sara` دسترسی حساب و نشست‌هایش را قطع می‌کند. کلید مشترک قبلی پذیرفته نمی‌شود. ثبت‌نام عمومی کارکنان وجود ندارد.

در `/reception/` و `/en/reception/` نمونهٔ ساختگی بدون ورود قابل بررسی است. در حالت واقعی نشست ۳۰ دقیقه اعتبار دارد؛ توکن فقط در حافظهٔ تب و هش آن در پایگاه داده نگهداری می‌شود. خروج، نشست سمت سرور را باطل می‌کند. تاریخچهٔ هر درخواست تا ۵۰ رویداد اخیر و برای تغییرهای جدید نام حساب مسئول را نمایش می‌دهد. اطلاعات بالینی در این صندوق نیست. استفاده از HTTPS الزامی است؛ راهنمای ورود دومرحله‌ای و بازیابی مدیریتی در ادامه آمده است؛ پنل مدیریت کاربران هنوز آماده نیست.

### ورود دومرحله‌ای کارکنان (جایگزین ورود صرفاً با رمز)
- پیش از ایجاد حساب، یک بار روی VPS در فایل خصوصی `.env` مقدار مستقل `STAFF_MFA_KEY` برابر خروجی `openssl rand -hex 32` بگذارید و `docker compose up -d --build` اجرا کنید. کلید رمزگذاری را جدا از بکاپ دیتابیس، امن نگهداری کنید؛ تعویض مستقیم آن رمزسازهای فعلی را غیرقابل استفاده می‌کند. ساعت سرور و دستگاه باید همگام باشد.
- `create` اکنون دو خط خصوصی چاپ می‌کند: گذرواژه و URI استاندارد `otpauth://` برای برنامهٔ رمزساز. برای ورود دستی، مقدار `secret` در URI را با تنظیمات TOTP، SHA1، شش رقم، ۳۰ ثانیه وارد کنید. URI را به سرویس‌های آنلاین QR ندهید. رمز و اطلاعات ثبت رمزساز را از دو مسیر امن تحویل دهید. هیچ کد نمونه یا ورود تک‌عاملی وجود ندارد.
- حساب‌های قدیمی و حسابی که گوشی‌اش را از دست داده: پس از احراز هویت کارکنان، مدیر میزبان `docker compose exec web node dist/staff-cli.js reset-mfa USER` اجرا کند. برای فراموشی رمز، `reset-password USER` اجرا شود. هر دو عملیات نشست‌های قبلی را باطل می‌کنند؛ هیچ‌کدام حساب غیرفعال را فعال نمی‌کند. پس از ارتقا همهٔ نشست‌های پیش از MFA باطل می‌شوند.

## تقویم ساعات آزاد
اپراتور پذیرش پس از ورود در قسمت «مدیریت ساعات آزاد دکتر رحمانی» نوع خدمت، شیوه، زمان شروع محلی تهران و مدت را مشخص می‌کند. محدوده انتشار ۹۰ روز است. PostgreSQL هم‌پوشانی بازه‌ها را برای همین متخصص حتی بین دو خدمت یا شیوهٔ مختلف رد می‌کند. برداشت زمان آن را از فهرست عمومی حذف می‌کند. پروفایل فارسی و انگلیسی از `GET /api/v1/availability` می‌خواند و در نبود ساعت منتشرشده خالی می‌ماند. مراجع می‌تواند پس از مرور انتخاب، زمان را موقتاً نگه دارد؛ رزرو قطعی و پرداخت هنوز فعال نیست. آزمون `apps/api/tests/availability.mjs` فقط روی محیط تست اجرا شود.

### نگهداری موقت
مهلت اولیهٔ آزمایشی ۱۰ دقیقه است. پیش از انتشار با تأیید مؤسسه `HOLD_MINUTES` (۱ تا ۳۰) را در `.env` تعیین کنید. انقضا و دسترسی به وقت بر اساس ساعت PostgreSQL بررسی می‌شود و به زمان‌سنج مرورگر یا اجرای job وابسته نیست. برای بازیابی بعد از تازه‌سازی، توکن در sessionStorage همان تب نگهداری می‌شود. هویت مراجع هنوز احراز نمی‌شود.

## حساب مراجع و نوبت‌های من
صفحات `/account/` و `/en/account/` برای ثبت‌نام با نام مستعار، ورود و مدیریت وقت‌های موقت‌اند. پس از نگهداری وقت، مراجع در همان تب وارد حساب می‌شود و اتصال وقت را تأیید می‌کند؛ مهلت تمدید نمی‌شود. از آن پس توکن مهمان برای مدیریت آن وقت قابل استفاده نیست. نشست یک ساعت اعتبار دارد. برای محیط تولید، HTTPS و دسترسی هم‌دامنه به API الزامی است. این حساب احراز هویت قانونی، پرداخت، یا نوبت قطعی ندارد. برای تست از حساب نمونه استفاده شود.

### تعرفهٔ جلسات
برای انتشار زمان جدید، پذیرش باید مبلغ مثبت صحیح به ریال وارد کند. مبلغ در همان رکورد زمان ثبت می‌شود و مبلغی از فرم مراجع دریافت نمی‌شود. زمان‌های قدیمی با تعرفهٔ نامشخص رایگان محسوب نمی‌شوند. ثبت تعرفه نه به معنی پرداخت است و نه صدور رسید.

### پیش‌فاکتور وقت موقت
مراجع از «نوبت‌های من» برای وقت فعالِ متصل به حساب با تعرفه مشخص، پیش‌فاکتور می‌گیرد. مبلغ ریالی و مهلت از پایگاه داده خوانده می‌شوند و برای هر نگهداری فقط یک پیش‌فاکتور ثبت می‌شود. ۲۰ پیش‌فاکتور اخیر با وضعیت اعتبار نمایش داده می‌شوند. آزادسازی یا انقضا پیش‌فاکتور را غیرقابل استفاده می‌کند. این سند رسید پرداخت، تمدید مهلت یا تأیید رزرو نیست. هیچ درگاهی فراخوانی نمی‌شود.

### بازیابی حساب مراجع
در نوبت‌های من، مراجع با تأیید گذرواژه از «امنیت حساب» یک کد بازیابی دریافت می‌کند. کد فقط هنگام صدور نشان داده می‌شود و تنها هش آن در پایگاه داده می‌ماند. کد جدید قبلی را باطل می‌کند. کد باید قبل از فراموشی رمز در محل امن ذخیره شود. از صفحهٔ ورود، کد و نام کاربری به همراه گذرواژهٔ جدید برای بازنشانی لازم‌اند. بازنشانی کد را مصرف و تمام نشست‌های حساب را باطل می‌کند؛ ورود خودکار انجام نمی‌شود. آزمون روی دیتابیس آزمایشی: `node tests/client-recovery.mjs` از پوشهٔ API با متغیرهای اتصال مطابق سایر آزمون‌ها.

### گزارش عملیاتی پذیرش
از پنل پذیرش، نقش‌های پذیرش و مشاهده‌گر گزارش تجمیعی را می‌بینند. چهار شاخص فعلی صف و تقویم از جدول روزانهٔ هفت روز تقویمی به وقت تهران جدا هستند. خروجی گزارش اطلاعات هویتی ندارد و نه پیش‌فاکتور را درآمد می‌داند نه وقت موقت را نوبت قطعی.

### شعب حضوری
اپراتور از مدیریت ساعات آزاد می‌تواند نام و نشانی دوزبانهٔ شعبه را منتشر، برای وقت حضوری انتخاب یا برای انتشارهای بعدی بایگانی کند. بایگانی محل جلسات قبلاً منتشرشده را عوض نمی‌کند. نشانی نمونه در سایت درج نشده و تعیین شعبه برای جلسهٔ آنلاین مجاز نیست.

### اتصال اختیاری به زرین‌پال (v4)
پیش‌نمایش بدون تنظیمات پذیرنده غیرفعال است. برای راه‌اندازی در VPS پس از تأیید تعرفه، سیاست لغو/بازپرداخت و دامنهٔ پذیرنده، `ZARINPAL_MERCHANT_ID` و `PUBLIC_ORIGIN` (فقط مبدأ HTTPS دامنهٔ ثبت‌شده، بدون اسلش پایانی) را در `.env` خصوصی میزبان تنظیم و سرویس را بازایجاد کنید. Callback: `/api/v1/payments/return`. دسترسی خروجی سرور به زرین‌پال ضروری است. این تنظیمات به سرویس واقعی وصل می‌شوند؛ پیش از انتشار عمومی آزمون کنترل‌شده با حساب پذیرنده لازم است. اطلاعات پذیرنده را در مخزن یا چت قرار ندهید.

مبلغ IRR از پیش‌فاکتور سرور خوانده می‌شود. برای هر پیش‌فاکتور یک authority ذخیره می‌شود. نتیجهٔ مرورگر تأیید مالی نیست؛ پس از verify موفق، ثبت مرجع و قطعی‌کردن وقت متعلق به همان حساب/نگهداری در یک تراکنش انجام می‌شود. اگر مهلت گذشته باشد یا وقت آزاد شده باشد، پرداخت تأییدشده با وضعیت review نگه داشته می‌شود، نه رزرو جدید. بازپرداخت خودکار فعال نیست؛ پیش از فعال‌سازی، مسئول و روال تطبیق و استرداد آن تعیین شود. اگر بازگشت از درگاه کامل نشد، گزینهٔ استعلام در حساب مراجع نتیجه را دوباره از درگاه بررسی می‌کند. تست محلی `tests/payments.mjs` از پاسخ شبیه‌سازی‌شده و PostgreSQL آزمایشی استفاده می‌کند و وجهی جابه‌جا نمی‌کند.

### برنامهٔ جلسات و ثبت حضور
صندوق پذیرش دو فهرست صفحه‌بندی‌شدهٔ جلسات قطعی دارد: پیش رو/در حال برگزاری، و پایان‌یافته. فقط اپراتور پذیرش می‌تواند بعد از پایان جلسه حضور یا عدم حضور را ثبت یا اصلاح کند. هر تغییر با نسخه، زمان و حساب اپراتور ثبت می‌شود و تغییر مبتنی بر نسخهٔ قدیمی رد می‌شود. مراجع در حساب خود ۲۰ جلسهٔ گذشتهٔ اخیر و وضعیت حضور را می‌بیند. این ثبت اداری است و اثری روی پرداخت یا پروندهٔ بالینی ندارد. حالت نمونهٔ پذیرش کاملاً محلی است.

### جابه‌جایی جلسهٔ قطعی
از بخش برنامهٔ جلسات در پذیرش، اپراتور پس از هماهنگی با مراجع می‌تواند یک جلسهٔ شروع‌نشده را به وقت آزاد هم‌خدمت، هم‌شعبه، هم‌شیوه، هم‌مدت و هم‌تعرفه منتقل کند. نشست‌های در حال برگزاری، زمان‌های تحت نگهداری فعال و مقصد نامنطبق پذیرفته نمی‌شوند. انتقال و ثبت شناسهٔ اپراتور و هر دو زمان در یک تراکنش انجام می‌شود؛ وقت قبلی دوباره آزاد می‌شود. شمارهٔ مرجع پرداخت و مبلغ ثابت می‌ماند. فعلاً اعلان خودکار ارسال نمی‌شود.

در حساب مراجع، ۲۰ تغییر وقت اخیر با زمان قبلی و جایگزین به وقت تهران نمایش داده می‌شود. برای هر جلسهٔ قطعی، فایل تقویم اختیاری با عنوان عمومی و یادآور یک ساعت قبل قابل دریافت است؛ این فایل اشتراک زنده نیست و بعد از جابه‌جایی باید جایگزین شود. هیچ پیامک یا ایمیلی ارسال نمی‌شود.

### درخواست بررسی لغو
مراجع برای جلسهٔ قطعی و شروع‌نشدهٔ خودش یک درخواست ثبت می‌کند. پذیرش آن را کنار جلسه می‌بیند و می‌تواند مشاهدهٔ درخواست را ثبت کند. این گردش‌کار نوبت را آزاد نمی‌کند، پرداخت را تغییر نمی‌دهد و جایگزین تصمیم نهایی مرکز یا بازپرداخت نیست.

پس از ثبت مشاهده، پذیرش می‌تواند درخواست را رد کند یا (پیش از شروع و برای همان وقت درخواست‌شده) لغو را تأیید کند. تصمیم نهایی یک‌بار با شناسهٔ اپراتور و زمان ثبت می‌شود. با تأیید، وقت آزاد می‌شود؛ با رد، نوبت برقرار می‌ماند. هنگام باز بودن درخواست، جابه‌جایی مجاز نیست. نتیجه در حساب مراجع نمایش داده می‌شود. هیچ بازپرداخت خودکاری انجام نمی‌شود.

### پیگیری مالی پس از لغو
در میز پذیرش، لغوهای تأییدشده با پرداخت قطعی در صف «پیگیری مالی نوبت‌های لغوشده» نمایش داده می‌شوند. اپراتور پذیرش می‌تواند بررسی را یک‌بار آغاز کند؛ نام مسئول و زمان شروع ذخیره می‌شود. مراجع در بخش نتیجهٔ درخواست‌های لغو، شروع بررسی را می‌بیند. مبلغ نمایش‌داده‌شده مبلغ پرداختی به ریال است، نه مبلغ قابل‌استرداد. این مرحله تصمیم بازپرداخت ثبت نمی‌کند و به درگاه پولی درخواست نمی‌فرستد.

مسئول ثبت‌شدهٔ هر بررسی می‌تواند یک بار مبلغ پیشنهادی استرداد را به ریال ثبت کند (از صفر تا مبلغ پرداخت). نتیجه در صف «بررسی‌شده» و در حساب صاحب نوبت نمایش داده می‌شود. این پیشنهاد مجوز پرداخت نیست و هیچ فراخوانی به درگاه انجام نمی‌دهد.

### تأیید مستقل پیشنهاد مالی
هیچ کارمندی به‌صورت پیش‌فرض مجاز به تأیید پیشنهاد نیست. پس از تعیین مسئول توسط مرکز، مدیر میزبان می‌تواند برای یک حساب پذیرش با `docker compose exec web node dist/staff-cli.js grant-refund USER` مجوز بدهد و با `revoke-refund USER` آن را بردارد. در «بررسی‌شده»، فقط مسئول مجاز دیگری (غیر از پیشنهاددهنده) می‌تواند مبلغ ثبت‌شده را یک بار تأیید یا رد کند. تصمیم با زمان و شناسهٔ تصمیم‌گیر ثبت می‌شود و مراجع نتیجه را می‌بیند. این عملیات هیچ انتقال بانکی ندارد.

### ثبت رسید استرداد خارج از سامانه
بعد از واریز واقعی خارج از سامانه، برای پیشنهاد مثبت و تأییدشده، مسئول دارای مجوز استرداد (غیر از پیشنهاددهنده) می‌تواند مبلغ روی رسید و مرجع واریز را ثبت کند. مبلغ باید دقیقاً مطابق تصمیم باشد. هر پرونده تنها یک رسید دارد و یک مرجع برای دو پرونده پذیرفته نمی‌شود. شناسهٔ ثبت‌کننده و زمان ثبت نگهداری می‌شود و مرجع در نتیجهٔ لغوِ حساب مراجع نمایش داده می‌شود. ثبت رسید به معنای استعلام از بانک نیست.

گزارش تطبیق استرداد در میز پذیرش، فقط مبالغ مثبت با تصمیم تأیید نهایی و پرداخت اصلی تأییدشده را در سه گروه «بدون رسید»، «رسید هم‌مبلغ» و «مغایرت مبلغ» نشان می‌دهد. تعداد و جمع ریالی مصوب و ثبت‌شده به کل گروه مربوط است؛ جزئیات در صفحه‌های ۲۰تایی نمایش داده می‌شود. این گزارش خواندنی است و با صورت‌حساب بانک ارتباط ندارد.

در گروه «مغایرت مبلغ»، اپراتور پذیرش می‌تواند مسئولیت پیگیری یک مورد را بپذیرد. فقط همان فرد می‌تواند یک‌بار نتیجهٔ اقدام («درخواست مدرک تکمیلی» یا «ارجاع به مسئول مالی») را ثبت کند. مالک و نتیجه کنار مبالغ دیده می‌شوند؛ ثبت اقدام رسید را اصلاح نمی‌کند و مغایرت را نمی‌بندد.

پس از ثبت اقدام پیگیری، مسئول پرونده شناسهٔ مدرک بیرونی و مبلغ مستند را وارد می‌کند (فایل یا اطلاعات کارت دریافت نمی‌شود). پاسخ تازه، پاسخ پیشین را حذف نمی‌کند. فقط مسئول دیگری با مجوز استرداد می‌تواند بر مبنای آخرین پاسخ هم‌مبلغ با تصمیم مصوب، پرونده را یک بار ببندد. گروه «بسته‌شده با مدرک» جدا از «رسید هم‌مبلغ» است: مبلغ رسید اولیه تغییر نمی‌کند و بستن پرونده تأیید بانکی نیست.

در «مقایسه با ردیف‌های صورت‌حساب»، مسئول دارای مجوز استرداد فقط دو ستون پالایش‌شده از برداشت‌های بانکی را وارد می‌کند: مرجع استرداد و مبلغ مثبت ریالی، با ویرگول انگلیسی و بدون سرستون. حداکثر ۱۰۰ مرجع یکتا؛ نمونه: `RF-1004,400000`. خروجی فقط ردیف‌های ورودی را با رسیدهای مرکز مقایسه می‌کند؛ فایل بانک، شمارهٔ کارت و اطلاعات هویتی نباید وارد شوند. این مقایسه داده‌ای در پایگاه ثبت نمی‌کند و اصالت صورت‌حساب را تأیید نمی‌کند.

### آزمون مرورگری گردش استرداد
فقط روی پایگاه آزمایشی خالی و مهاجرت‌یافته و نمونهٔ محلی در پورت ۸۰۸۰ اجرا کنید. پس از ساخت وب و API، از `apps/api` با `PGHOST`، `PGPORT`، `PGDATABASE`، `PGUSER`، `PGPASSWORD` و `STAFF_MFA_KEY` یکسان با سرویس، دستور `REFUND_E2E=1 node tests/refund-browser.mjs` را اجرا کنید. مرورگر پیش‌فرض Chromium همراه بستهٔ توسعه برای لینوکس است و به کتابخانه‌های اجرایی Chromium نیاز دارد؛ در صورت نصب مرورگر سازگار، مسیر آن را با `CHROME_BIN` مشخص کنید. آزمون با یک لغو تأییدشدهٔ ساختگی شروع می‌کند و دو حساب موقت مستقل با رمز یک‌بارمصرف می‌سازد. بررسی، تأیید، ثبت رسید و مقایسه با ردیف ساختگی صورت‌حساب در رابط انگلیسی انجام می‌شود. داده‌های مختص آزمون در پایان پاک می‌شوند. هیچ ارتباط بانکی برقرار نمی‌شود.

برای اجرای همین آزمون در پنل فارسی، `E2E_LOCALE=fa` را به محیط اجرای آزمون اضافه کنید. آزمون راست‌به‌چپ بودن صفحه، ورود با کد فارسی و مقایسه با ویرگول و ارقام فارسی را نیز بررسی می‌کند. در ردیف صورت‌حساب ارقام فارسی، عربی و لاتین و هر دو ویرگول `،` و `,` پذیرفته می‌شوند؛ مبلغ باید صحیح و بدون جداکنندهٔ هزارگان باشد. برگهٔ اجرای دستی کارکنان در `docs/refund-acceptance-fa.md` است.

راهنمای پشتیبان رمز‌شده و تمرین بازیابی جدا از پایگاه عملیاتی: [بازیابی روی VPS](docs/vps-backup-fa.md).

نمونهٔ تایمر روزانهٔ systemd، انتقال SFTP با بازخوانی فایل و هشدار شکست در همان راهنمای بازیابی توضیح داده شده‌اند.

### شهریهٔ آکادمی
مسیر پرداخت شهریه از پرداخت جلسات جدا است و به‌صورت پیش‌فرض بسته است (`ACADEMY_CHECKOUT=disabled`). پس از پذیرش عملیاتی، فعال‌سازی به `ACADEMY_CHECKOUT=enabled`، شناسهٔ معتبر درگاه و `PUBLIC_ORIGIN` امن نیاز دارد. رزرو ظرفیت هنگام صدور درخواست پرداخت تا ده دقیقه و حداکثر تا شروع دوره معتبر است. بازگشت مرورگر تأیید پرداخت نیست؛ سرور مبلغ ثبت‌شده را استعلام می‌کند. پرداخت تأییدشدهٔ دیرهنگام بدون ثبت‌نام در وضعیت بررسی می‌ماند؛ بازپرداخت خودکار نیست. آزمون `apps/api/tests/cohorts.mjs` از پاسخ‌های شبیه‌سازی‌شدهٔ درگاه و PostgreSQL واقعی استفاده می‌کند؛ این آزمون جای تست پذیرش درگاه نیست.

### آزمون و گواهی داخلی آکادمی
پذیرش پس از پایان آموزش، آزمون نوبتی را که شروع شده باز می‌کند. فقط مراجع ثبت‌نام‌شده در حساب خود می‌تواند پاسخ نهایی بدهد. آزمون اولیه شامل دو سؤال دوزبانهٔ ثابت برای هر دوره است؛ قبولی به دو پاسخ درست نیاز دارد. ارسال دوباره نتیجه را تغییر نمی‌دهد. گواهی داخلی از `/academy/verify/` و `/en/academy/verify/` با شناسهٔ تصادفی قابل استعلام است؛ خروجی عمومی فقط نام دوره (از روی کد دوره) و تاریخ قبولی را نشان می‌دهد، نه نام و حساب مراجع. این گواهی مدرک حرفه‌ای نیست؛ محتوا و حدنصاب باید قبل از استفادهٔ رسمی به تأیید مرکز برسند.

### شهریه‌های تأییدشده بدون ثبت‌نام
اگر پرداخت شهریه بعد از تکمیل ظرفیت تأیید شود، حساب مراجع در وضعیت «در انتظار بررسی» می‌ماند. پذیرش در میز کار خود مورد را «شروع بررسی» می‌کند؛ سپس «پذیرش و ثبت‌نام» (حتی بیرون از ظرفیت، با تأیید صریح) یا «رد کردن» را ثبت می‌کند. هیچ‌کدام واریز یا بازپرداخت ثبت نمی‌کند؛ «رد کردن» فقط تصمیم مرکز را ثبت می‌کند و بازپرداخت همچنان از مسیر مالی جداگانه انجام می‌شود. این تصمیم داوری نیست و توسط پذیرش گرفته می‌شود. آزمون `apps/api/tests/cohorts.mjs` claim/resolve، رد ثبت‌نام دوباره و ثبت قطعی با تصمیم مرکز را با PostgreSQL بررسی می‌کند.

### پنل متخصص و پنل مدیریت (نسخه اول)
نقش‌های `specialist` و `manager` به کارکنان اضافه شدند (`staff-cli create USER specialist|manager`؛ ورود با همان حساب MFA در `/reception/`). متخصص برنامهٔ جلسات قطعی را می‌بیند و فقط تجمیع درآمد ماهانهٔ ۱۲ ماه اخیر را (بدون دادهٔ بالینی و بدون هویت مراجع). مدیر نمای کلی عملیات (شمارش درخواست تماس هفته، پرداخت‌های تأییدشده و واریزهای ثبت‌شدهٔ ماه، جلسات پیش رو، ثبت‌نام‌های آکادمی، صف‌های باز) را می‌بیند و حساب‌های غیرمدیری را فعال/غیرفعال می‌کند؛ غیرفعال‌سازی نشست‌ها را باطل می‌کند. ساخت حساب فقط روی سرور با CLI است. هر دو صفحه فقط خواندنی‌اند و وجهی جابه‌جا نمی‌کنند.

### مجلهٔ مرکز؛ ارسال و بازبینی سردبیر
بازدیدکننده می‌تواند متن خود را از صفحهٔ مجله (`/journal/` و `/en/journal/`) بفرستد (محدودیت نرخ مثل فرم تماس). متن فقط با تأیید کاربر `manager` منتشر می‌شود؛ این بررسی سردبیری است، نه داوری رسمی همتا. خروجی عمومی انتشار فقط عنوان، نام نویسندهٔ انتخابی، چکیده، متن و تاریخ انتشار را می‌دهد؛ ایمیل هرگز عمومی نمی‌شود. تصمیم سردبیر یک‌باره ثبت می‌شود.

### اتاق جلسهٔ آنلاین (Jitsi)
برای نوبت قطعی آنلاین، مراجع از دکمهٔ «ورود به اتاق جلسهٔ آنلاین» در حسابش پیوند اختصاصی و حدس‌ناپذیر Jitsi (`https://meet.jit.si/rahmani-<128-bit>`) می‌گیرد؛ ساخت اتاق یا نمایش پیوند فقط با همان نشست مراجع و فقط تا ۱۵ دقیقه پس از پایان جلسه ممکن است. ضبط پیش‌فرض انجام نمی‌شود. این پیوند جایگزین کنترل دسترسی سازمانی نیست؛ پیش از جلسات واقعی، مرکز باید نسخهٔ میزبانی‌شدهٔ خود Jitsi یا ارائه‌دهندهٔ قراردادی (با تالار انتظار و احراز هویت) را انتخاب کند.

## ثبت پرداخت حضوری (نقدی) و صندوق پذیرش

- پذیرش می‌تواند از پنل «ثبت پرداخت نقدی (حضوری)» نوبت‌های حضوری قطعی‌نشده را ببیند، با ردیف «تخفیف» اختیاری مبلغ را ثبت کند؛ با ثبت، نوبت قطعی می‌شود و رسید `CASH-…` صادر می‌گردد.
- `POST /api/v1/reception/cash/record` فقط نقش `reception`؛ نوبت‌های آنلاین با `409` رد می‌شوند؛ ثبت دوباره با `409` جلوگیری می‌گردد.
- رسید نقدی در صفحهٔ «حساب من» مرجع پرداخت می‌شود؛ جمع‌های «درآمد این ماه» مدیر و گزارش متخصص، آنلاین و نقدی را با هم نشان می‌دهند.
- تنظیمات عمومی سایت (شمارهٔ تماس، ایمیل، آدرس، ساعات کار، اینستاگرام/تلگرام/وب‌سایت https) از پنل مدیر «تنظیمات سایت» قابل تغییر است و در صفحهٔ «تماس با مرکز» نمایش داده می‌شود.
- شکایت و بازخورد: فرم عمومی در صفحهٔ «تماس با مرکز»؛ صف پیگیری در پنل پذیرش (`تازه → در حال پیگیری → بسته`). هیچ دادهٔ بالینی ذخیره نمی‌شود.

## پروندهٔ بالینی رمزگذاری‌شده

- ماژول جدا (`clinical` schema) با رمزنگاری AES-256-GCM و کلید مستقل `CLINICAL_KEY`؛ فقط نقش `specialist` از پنل «یادداشت‌های بالینی» به آن دسترسی دارد.
- متن برای مدیر، پذیرش و مراجع قابل مشاهده نیست؛ هر «خواندن» در `clinical.access_log` ثبت می‌شود.
- بدون `CLINICAL_KEY` ماژول با 503 خاموش می‌شود و سایت عمومی سالم می‌ماند (تست شده). تولید کلید: `openssl rand -base64 32`.
- این سامانه retention/چرخش کلید و ممیزی ASVS بیرونی ندارد؛ قبل از دادهٔ واقعی تعیین کنید.
